# ADR-0012: Text first, OCR on demand, vision as a distinct reading

**Status:** Accepted · **Date:** 2026-08-26 · **Amended by** [ADR-0028](0028-reading-and-readingmode.md)

## Context

The simplest possible design for this library is one sentence: send the
document to a vision model and ask for JSON. Frontier vision models are good.
In early 2026 general-purpose models overtook dedicated OCR engines on the OCR
Arena leaderboard, and vision-language models show three to four times lower
character error rate than traditional engines on noisy scans and receipts.

If that were the whole picture, ovrin would be a thin wrapper and would not
need to exist.

It is not the whole picture, on three counts.

**Staged beats direct, measurably.** Published work on long scanned financial
documents finds that a multistage pipeline consistently outperforms the direct
PDF-to-VLM baseline by a substantial margin. Handing a model raw pages and
asking for structure does worse than recovering text carefully and then
extracting from it.

**Cost.** Vision-model pricing is per token and page images are expensive. For
high-volume structured documents, per-document OCR pricing is dramatically
cheaper. A 40-page bank statement through a vision model, monthly, across a
customer base, is a budget line somebody will notice.

**The text layer is already right.** For a PDF generated by Word or LaTeX, the
characters are in the file. Rendering them to pixels and asking a model to read
the pixels back is a lossy round trip that can only introduce error into data
that was exact.

The counter-case is real too: for variable layouts and poor-quality scans,
models beat OCR decisively. So the answer is not "OCR is better" — it is that
the right reading depends on the document, and the pipeline should choose.

## Decision

Content acquisition is staged, and each stage is attempted only when the
previous one is insufficient.

```text
Source
  ├─ text layer present and usable? ──── yes ──> use it. Done.
  │                                  no
  ├─ an OCR provider configured? ─────── yes ──> rasterise if needed, OCR.
  │                                  no
  └─ a vision-capable Model? ─────────── yes ──> page images to the model.
                                     no
                                          error, naming all three remedies
```

Three properties of this that matter more than the order:

**Vision is a reading, not a shortcut.** When page images go to the model, they
go through the same normalisation, prompting and validation as OCR text. It is
another way to acquire content, not a bypass around the pipeline.

**The caller can override.** `WithReading(ovrin.ModeVision)` forces a
specific strategy. The default is adaptive; a caller who knows their corpus can
do better than the default and should be allowed to.

**Readings can be combined, not just chosen.** When two readings are available,
running both is what makes cross-validation possible
([ADR-0014](0014-cross-validation.md)) — which is the strongest quality signal
ovrin has. It costs twice as much, so it is opt-in via
`WithReading(ovrin.ModeBoth)`, not the default.

## Consequences

**Good.** The common case — a text-layer PDF — is fast, exact and nearly free,
with no model call needed to acquire content. Cost scales with document
difficulty rather than document count. The design is backed by published
comparison rather than preference. And because readings are pluggable and
comparable, cross-validation falls out of the same structure instead of needing
a separate mechanism.

**Bad.** Three acquisition paths is three code paths, three sets of failure
modes, and three things to explain. "Usable text layer" is a heuristic, and
heuristics are wrong sometimes — a PDF with a broken `ToUnicode` table can
produce plausible-looking rubbish that passes the usability check and poisons
everything downstream. Performance becomes hard for a user to predict, since
two superficially similar PDFs can take paths that differ by two orders of
magnitude in cost and latency. And ovrin will sometimes choose OCR where a
vision model would have done better, because it cannot know the scan quality
before it commits.

**Neutral.** The usability heuristic — character count per page area, ratio of
replacement characters, presence of a `ToUnicode` map — is documented in
[`docs/pipeline.md`](../pipeline.md) and its thresholds are configurable. It
will be tuned against the evaluation corpus, and its current values are not
claimed to be optimal.

## Alternatives considered

- **Vision-only: always send page images.** Rejected: measurably worse than a
  staged pipeline, considerably more expensive, and lossy on documents whose
  text is already exact. It is also a product anyone can build in an afternoon,
  which is a sign it is not the product.
- **OCR-only: always rasterise and OCR.** Rejected: discards an exact text
  layer in favour of an approximation, and makes a renderer mandatory.
- **Always run every available reading and merge.** Rejected as a default:
  best accuracy, worst cost, on every document including the easy ones.
  Available as `ModeBoth`.
- **Let the caller choose, with no default.** Rejected: forces every user to
  understand the trade-off before their first extraction. The default should be
  the right answer for someone who has not read this ADR.
