# ADR-0011: PDF text-layer extraction is written in-tree

**Status:** Accepted · **Date:** 2026-08-26

## Context

Most PDFs are not scans. They are generated by Word, LaTeX, Chrome's print
pipeline or a reporting engine, and they carry a text layer — the actual
characters, with positions. Reading that layer is faster, cheaper and more
accurate than any OCR or vision model, and it is the path the majority of ovrin
users will take. It has to be good.

"Reading the text layer" is more than pulling strings out of content streams.
It requires the cross-reference table, object streams, FlateDecode and the
other filters, font encoding and `ToUnicode` CMaps to map glyph codes back to
characters, and text-positioning operators to reconstruct reading order,
columns, spaces and line breaks. A PDF that renders correctly can still yield
gibberish if the encoding is handled naively.

The Go options:

- **`pdfcpu/pdfcpu`** — Apache-2.0, pure Go, actively maintained, excellent at
  document operations. Text extraction is present but is not its centre of
  gravity, and position-aware extraction has been a long-running request.
- **`ledongthuc/pdf`** — a continuation of one of the oldest Go PDF libraries.
  Extracts text and styling. Small, permissive, lightly maintained.
- **`unidoc/unipdf`** — the most capable by a distance. Dual-licensed:
  **AGPL** or paid commercial. Rule
  [§4.4](../rules.md#4-dependencies) excludes it, and a paid licence for a
  library's own dependency is not viable for downstream users.

And rule [§4.1](../rules.md#4-dependencies) says the core has zero external
dependencies — which none of the above satisfies.

## Decision

**PDF text-layer extraction is implemented in `internal/pdf`, in the core
module, with no external dependency.** Scope is deliberately narrow: parse the
structure, decode the filters the standard library already provides
(`compress/zlib` for FlateDecode; LZWDecode, ASCII85 and ASCIIHex by
hand), resolve font encodings and `ToUnicode` CMaps, and reconstruct text with
positions from the text-showing operators.

What it does **not** do: render, edit, sign, encrypt, fill forms, or handle
colour and imaging. Those are the hard parts of PDF and ovrin needs none of
them. This is a reader for one purpose, and that is what makes it tractable
where a general PDF library would not be.

Explicit non-goals, each surfaced as a clear error rather than a bad result:

- Encrypted PDFs are refused, naming the encryption. Password support is a
  later ADR.
- Filters we do not implement (JBIG2, JPX for text purposes) are refused by
  name.
- A page whose text layer decodes to nothing usable reports "no usable text
  layer" and the pipeline falls through to OCR
  ([ADR-0012](0012-text-first-ocr-on-demand.md)) — it never returns partial
  gibberish as though it were text.

Quality is held by the evaluation corpus
([ADR-0023](0023-evaluation-corpus.md)), which includes PDFs from Word, LaTeX,
Chrome print, Excel export and at least two reporting engines, with expected
text committed alongside.

If this proves to be a mistake, the fallback is a `render`-style optional
module wrapping `pdfcpu`, and the seam is already shaped for it.

> **Correction, 2026-08-26.** This section originally listed `compress/lzw`
> among the filters the standard library provides. **It cannot be used.** PDF's
> LZWDecode defaults to `EarlyChange 1`, meaning the code width grows one code
> earlier than in the GIF and TIFF variant; `compress/lzw` implements the
> latter and exposes no parameter for it. The difference does not raise an
> error — it produces wrong bytes from the first table growth, which is the
> worst possible failure for a filter feeding a text extractor. The decoder is
> written in-tree, with `earlyChange` as a parameter, and its
> `earlyChange=false` path is cross-checked against `compress/lzw` in a test.
>
> Found while implementing, and recorded rather than quietly fixed, because the
> decision below rests partly on how much the standard library gives us for
> free — and it gives us slightly less than this ADR claimed.

## Consequences

**Good.** The core keeps its zero-dependency property, which is the single
constraint that makes ovrin trivially adoptable. No AGPL exposure. We control
the failure modes — "no usable text layer" is a decision we make deliberately
rather than an empty string we have to interpret. Extraction produces positions
directly, which provenance ([ADR-0015](0015-provenance.md)) needs and which no
Go library gives us cleanly today. Hardening is ours to do
([ADR-0020](0020-resource-limits.md)).

**Bad.** This is the largest piece of work in v0.1 by a wide margin, and PDF is
a specification with thirty years of divergent implementations behind it. We
will be wrong about real files, repeatedly, and each wrong file is a bug report
with a document attached that we may not be able to redistribute. `pdfcpu` has
years of accumulated fixes for malformed files that we will rediscover one at a
time. Font encoding in particular — CID fonts, custom encodings, broken
`ToUnicode` tables — is a long tail with no end. And a maintainer writing a PDF
parser is a maintainer not writing the confidence engine, which is the part of
ovrin nobody else has.

We accept it because the alternative is either an AGPL dependency, which is
disqualifying, or breaking the zero-dependency rule for a library that does not
give us positions anyway.

## Alternatives considered

- **`pdfcpu` as a core dependency.** Rejected: breaks rule
  [§4.1](../rules.md#4-dependencies). The strongest alternative, and the one to
  reconsider first if in-tree extraction proves too costly — Apache-2.0, pure
  Go, actively maintained.
- **`ledongthuc/pdf` as a core dependency.** Rejected: same rule, and less
  actively maintained than `pdfcpu` for a comparable feature set.
- **`unipdf`.** Rejected: AGPL or paid, rule
  [§4.4](../rules.md#4-dependencies).
- **Skip the text layer; rasterise and OCR everything.** Rejected: slower and
  worse on the majority case, and it makes a renderer mandatory, which
  [ADR-0010](0010-no-cgo-in-core.md) works hard to avoid.
- **An optional `ovrin/parse/pdfcpu` module, with no in-core extractor.**
  Rejected for v0.1: it makes the most common document type require an optional
  module, so the quickstart cannot read a PDF without a second `go get`.
