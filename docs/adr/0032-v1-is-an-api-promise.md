# ADR-0032: v1.0 is a promise about the API, not about accuracy

**Status:** Accepted · **Date:** 2026-09-06 · **Supersedes the v1.0 gate in**
[ADR-0024](0024-versioning-and-stability.md)

## Context

[ADR-0024](0024-versioning-and-stability.md) set four conditions for v1.0, all
of them about evidence: a corpus of real documents with reports across two
provider generations, calibrated confidence with published expected calibration
error, an outside production deployment, and no known API change we would want
to make.

Three of those four are not met, and this ADR exists because pretending
otherwise would be worse than changing the rule:

- **The corpus is synthetic.** All twenty-five documents under `eval/corpus/`
  carry `source: synthetic`. They were generated by `eval/corpusgen` and are
  useful for testing the harness; they are not real documents.
- **No accuracy figure has been produced.** `eval/report/` holds only
  `no-run.json` and `no-run.md`, and `no-run.md` says of itself that every
  figure in it "is a zero produced by the report renderer over an empty set of
  results, not a measurement".
- **Nobody outside the project has run this in production**, or if they have,
  no feedback has come back and been incorporated.

The fourth condition — no known API change we would want — is met in the sense
that matters, and that turns out to be the whole point.

**ADR-0024 conflated two different promises.** A semantic version is a
statement about *compatibility*: v1.0 means the public API will not break
without a v2. It says nothing about whether the library is any good at its job.
By gating a compatibility promise on accuracy evidence, ADR-0024 made v1.0
unreachable for reasons that have nothing to do with what v1.0 actually means,
and left the project unable to offer stability to the people most likely to
want it — the government and banking users ADR-0024 itself names as
disproportionately unwilling to take a v0 dependency.

The API case stands on its own. Three additions are wanted and documented:
cache-read and cache-write fields on `Usage`, a handwriting kind on `Word`, and
rendering `Layout.Pairs` into the prompt. **All three are additive.** `Usage`
and `Word` are plain structs, so a new field breaks no caller. `Layout.Pairs`
rendering is internal behaviour and not surface at all. The changes that would
genuinely break people are new methods on the interfaces users implement —
`OCR`, `Model`, `Renderer`, `DocumentOCR`, `Scorer` — and none is wanted.

## Decision

**v1.0.0 promises the public API. It promises nothing about accuracy.**

Concretely, from v1.0.0 onward:

- The exported API of every module in this repository is stable. Breaking
  changes require a major version, as Go's module system already enforces
  through the `/v2` import path.
- `api/ovrin.txt` becomes a compatibility contract rather than a drift
  detector. `TestAPI` already fails on any change; after v1.0.0 a *removal or
  signature change* in that diff is a release blocker, not a regeneration.
- **Accuracy remains unmeasured, and every statement saying so stays.**
  `Result.Confidence` continues to document itself as a ranking signal and not
  a probability until the weights are calibrated. `docs/validating.md`
  continues to tell a prospective user exactly what has and has not been
  demonstrated.

The stability judgement rests on the maintainer's own testing of the library
against real documents. That is a legitimate basis for an API promise and it is
recorded here as what it is, rather than presented as corpus evidence it is
not.

ADR-0024's three evidence conditions are **not withdrawn**. They remain the
conditions for saying ovrin is *accurate*, and they are tracked in
[`docs/roadmap.md`](../roadmap.md). What changes is that they no longer gate
the version number, because the version number was never the right place to
express them.

## Consequences

**Good.** People who could not take a v0 dependency can now take this one, and
the promise they are being given is one the project can actually keep — the API
is settled, and the compiler enforces it. The remaining uncertainty is stated
in the place a reader looks for it rather than encoded in a version number
nobody decodes correctly. Separating the two promises also means the accuracy
work can proceed on its own timetable without a release hanging on it, and
without the temptation to declare a synthetic corpus sufficient in order to
reach a version number.

**Bad.** A v1.0.0 with unmeasured accuracy will be read by some people as a
claim of maturity the project has not earned, and no amount of careful wording
in `docs/validating.md` reaches somebody who read the version number and
stopped. The three additive changes will now arrive as minor releases rather
than being folded into a pre-v1 churn, which means more releases and more
changelog for users to read. And the API is now genuinely frozen: a design
mistake found in six months is fixed in a v2 with a new import path, or lived
with. That is the actual cost of this decision, and it is paid in full — the
freedom to change `Result` on a whim is gone.

There is also an honest asymmetry worth naming. The maintainer's testing is
real but it is one person's, on their documents. ADR-0024's third condition
existed precisely because a single perspective misses things, and dropping it
from the gate does not make that less true. It makes early bug reports more
valuable and more likely, and `SUPPORT.md` should read like it expects them.

## Alternatives considered

- **Meet the four conditions first.** Correct, and the reason ADR-0024 was
  written. Rejected because two of them are not the maintainer's to satisfy: an
  outside production deployment requires an outsider, and a corpus of real
  redistributable documents requires people willing to contribute them. Waiting
  indefinitely for those while refusing stability to the users who would supply
  them is a deadlock, and v0 is what sustains it.

- **Declare the conditions met.** Rejected outright. The corpus is synthetic
  and the only report is a placeholder of zeros; writing anything else into an
  ADR would put a claim in the repository that the repository's own files
  contradict, in the one document set whose value is that it says what was
  actually decided and why.

- **Ship v1.0.0-rc.1 first.** Honest, and it makes no stability promise while
  gathering feedback. Rejected as the wrong instrument: a release candidate is
  for code whose *correctness* is in question pending testing, and the testing
  has happened. What is unmeasured is accuracy, which an rc period does not
  measure either.

- **Redefine v1.0 as "the API is stable" without an ADR.** Rejected. ADR-0024
  is an accepted decision that says the opposite in plain terms. Contradicting
  it silently would leave the next reader with two documents disagreeing and no
  record of which won, which is the failure the ADR practice exists to prevent.
